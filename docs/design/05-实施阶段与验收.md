# 实施阶段与验收

## 1. 交付顺序

先用最小本地闭环证明打包和跨平台，再补工作台、下载、AI与发布。每阶段交付可运行切片，尚未通过的能力不显示为已支持。

```mermaid
flowchart LR
  P0[P0：包内引擎技术切片] --> P1[P1：本地工作台与持久事实]
  P1 --> P2[P2：匿名平台真实下载]
  P1 --> P3[P3：自备模型API与报告]
  P2 --> P4[P4：恢复与正式发布]
  P3 --> P4
  P4 --> P5[P5：身份、浏览器、本地模型专项]
```

P2与P3可由不同人员并行，但必须共用同一个已稳定的任务、文件、协议和持久化基础；不能分别建立任务引擎。

## 2. P0 · 包内引擎与跨平台技术切片

估算5–8人日。目的：尽早发现冻结、原生依赖、协议和播放的阻塞。

| 任务 | 具体交付 |
| --- | --- |
| 建立独立工程 | Electron/React最小本地窗口、pnpm与uv锁文件、项目规范、格式与类型检查 |
| 建立协议与监督 | engine hello、schema版本、单实例、限长、stdout协议、stderr脱敏、shutdown |
| 冻结与资源 | onedir引擎、FFmpeg/ffprobe、候选yt-dlp+ejs/JSruntime、manifest与资源路径 |
| 最小本地事实 | 一个SQLite schema、一个导入任务、一个资产、hash/probe、缩略图 |
| 系统适配验证 | 中文/空格路径、无Python/Node/PATH依赖、原生Job Object适配、文件/目录同步、MP4受控播放 |
| 构建矩阵 | macOS arm64/x64、Windows x64内部安装包；签名链路先做可行性检查 |

退出条件：对应三套目标环境从安装包启动 → 选择MP4 → 真实probe和封面 → 播放 → 退出重启后资产仍在；断网完成该流程。直接终止Main、引擎或task-worker时，FFmpeg/下载器等子树仍被相应监督器回收，记录实际覆盖的故障范围。记录启动时间、基础包体积和空闲内存，给出实际测量基线。

如缺少Intel Mac/Windows环境，标记该架构未验收，并安排真实设备或虚拟化环境补证据；不能用Apple Silicon上的开发运行替代Windows/Intel安装验收。P0资源不能成立时先修正方案，再开发大量页面。

## 3. P1 · 本地工作台、存储与恢复基础

估算7–10人日。

| 任务 | 具体交付 |
| --- | --- |
| 桌面信息架构 | 工作区、任务、媒体库、剧本/报告、设置；移植纯控件和展示组件 |
| 类型与状态 | 契约生成、任务快照、revision/seq、事件重连与事实查询 |
| 文件管理 | 引用/托管模式、库目录、missing/changed、relink、受控输入快照、原生定位/导出 |
| 文档导入 | 文本、文字型PDF、DOCX的提取、编码与资源限制 |
| 持久任务 | 单owner、并发池、operation幂等、取消与重启协调 |
| 文件事务 | 暂存/验证/发布意图、原子rename与故障恢复 |
| 数据维护 | 版本化SQL迁移、一致性备份/恢复、缓存清理、保留媒体原件 |

退出条件：断网导入和浏览；取消和强制结束后没有重复记录或半文件成功，旧attempt迟到结果/恢复登记不能覆盖cancelled；文件移动、源文件处理中被修改、外接盘断开、磁盘不足可判定；备份恢复能核对数据与hash。

## 4. P2 · 匿名下载闭环

估算8–12人日，以少量平台为边界；平台变动或额外proof适配可能增加工作量。

| 任务 | 具体交付 |
| --- | --- |
| 规则迁移 | Registry限定、public判定、语义规格、错误分类、下载前重解析 |
| 网络治理 | DNS/redirect/媒体清单资源、直连/显式代理、超时与重试 |
| 受控执行 | 下载参数白名单、隔离暂存、插件加载、FFmpeg合并、进度分阶段 |
| 文件验证 | 大小/hash、媒体轨、原始时长与可交付完整性；保护负例 |
| 续传与取消 | format/context不一致时重做；有限续传；真正子树退出后确认取消 |
| 候选平台 | Bilibili公开单视频、YouTube公开单视频分别做安装态验证 |

退出条件：至少一个候选平台在macOS arm64、macOS x64、Windows x64三套安装制品均交付完整真实文件，经过播放和相应全片校验；另一候选只有全部通过才加入通用支持清单。受控HTTPS MP4夹具用于稳定测试，但不能替代真实平台验收。记录样本、时间、OS/架构、版本、匿名/身份、出口、hash、probe和结果，日志不含敏感URLquery。若某架构未验收，明确限制该制品的支持能力，不沿用其他架构的结果。

保护内容与网络失败分别归类，403不自动写成DRM。解析元数据成功、Cookie可读、注册平台数均不作为完整文件验收。

## 5. P3 · BYOK AI与报告

估算6–10人日；依赖P1的文件、任务和协议，可与P2并行。

| 任务 | 具体交付 |
| --- | --- |
| Provider设置 | endpoint/model/能力探测、safeStorage写入/删除、状态与有限超时 |
| 视频预处理 | 已校验的输入快照与hash绑定、抽帧上限、时间证据、源文件并发修改、失败/取消隔离 |
| 首批Skills | 综合/分镜/高光/文章/剧本，迁移必要references/modules及license |
| 步骤账本 | started先提交、succeeded、unknown、结果hash与明确重试决策 |
| 结果校验 | 严格schema、连续时间轴、证据关联；模型文本不直接执行 |
| 本地报告 | 带源文件和Skill版本、播放器时间跳转、Markdown/DOCX导出 |

退出条件：三套安装制品分别用一个真实视觉Provider完成视频分析、一个真实文本Provider完成剧本分析；如同一Provider同时满足能力可复用。输出经schema校验，报告可离线阅读/导出；测试调用中断后不自动再次计费。模型失败不影响下载与本地媒体；能力验收按OS/架构记录。

真实Provider验收使用用户另行提供的授权凭据及预算；本规划未读取或调用任何模型凭据。未完成真实模型验收时标记对应能力未验收，不以mock通过代替。

## 6. P4 · 故障收敛与正式发布

估算6–10人日；依赖P2和P3形成首版业务闭环。

| 任务 | 具体交付 |
| --- | --- |
| OS与生命周期 | 睡眠/唤醒、退出提示、进程树、文件锁、中文用户名、权限拒绝 |
| 运行边界 | IPCsender/参数、媒体路径、Markdown、大小限制、代理与SSRF专项回归 |
| 发布 | 应用图标/版本、每用户安装、签名、公证/staple、hash与notices |
| 升级演练 | 旧版本数据升级、失败恢复、密钥可访问、卸载保留用户媒体 |
| 性能与体验 | 限额、队列响应、缓存、错误提示、键盘操作和真实播放 |
| 使用文档 | 安装、目录、BYOK配置、备份、问题诊断；支持清单依据真实结果 |

退出条件：三套目标制品安装与运行验收，macOS正式签名公证及离线Gatekeeper检查、Windows签名/安装/卸载；每套制品声明的真实平台和模型闭环通过；升级失败可恢复原数据；没有仍被列为支持能力的阻塞问题。

## 7. P5 · 后续专项

这些能力不阻塞首版：

| 专项 | 依赖与退出条件 | 初步工作量 |
| --- | --- | --- |
| Chrome身份与登录平台 | 独立扩展分发/配对、双向认证、权限/材料清理、每平台正负完整文件 | 10–20人日，不含新平台逆向不确定性 |
| 浏览器阶梯 | macOS/Windows browser adapter、资源包、profile锁、取消/崩溃、多进程与出口验证 | 8–15人日 |
| 已有本地模型连接 | 本地运行时探测、文本/视觉能力、资源和质量、阻断外网后真实分析 | 4–8人日；不含内置GPU/runtime与模型分发 |
| 批量与来源发现 | 有界批量、取消/恢复、磁盘与平台频控，不建立第二调度器 | 5–10人日 |
| 自动更新 | 静态feed、关闭开关、ZIP/NSIS载荷、签名和迁移演练 | 3–5人日 |

各专项按使用价值单独立项，先完成一个平台或一种模型的完整流程；不要求首版复刻所有服务器功能。

## 8. 工作量与资源

P0–P4合计约32–50人日。以一名熟悉当前栈的全栈工程师估算约7–10个工作周；两人可在基础稳定后并行下载与AI，通常约5–7周。估算包含基本测试和发布演练，是范围判断，不是交付承诺。

主要变化因素：目标设备是否齐备、签名账户/证书、公网出口、平台proof/browser需求、第三方binary/wheel可用性与真实模型质量。平台专项、全部登录线路和完整离线模型不在32–50人日范围内。

需要的资源：macOS arm64与x64构建/运行环境、Windows x64环境、Apple正式分发身份、Windows签名方案、用于下载与模型验收的合法样本和授权配置。它们是后续实施与发布的输入，本次规划不创建外部仓库、购买证书或发布制品。

## 9. 验收矩阵

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 无自部署服务器 | 不配置server URL，不连接PG/Redis/MQ/MinIO/Temporal，仍能启动与本地工作 |
| AC-02 | 全新安装 | 无系统Node/Python/FFmpeg、无sibling源码，三套制品均运行真实任务 |
| AC-03 | 完全断网 | 本地导入、probe、播放、历史和已有报告导出正常 |
| AC-04 | 大文件 | 至少一个超过4 GiB且在产品上限内的MP4，流式hash/复制，不按文件大小涨内存 |
| AC-05 | 路径与权限 | 中文/空格/长路径、文件移动、只读目录、外接盘缺失，状态可判定且不误删 |
| AC-06 | 任务取消 | 下载/FFmpeg/分析取消覆盖子树，旧attempt/恢复登记不能覆盖已取消终态 |
| AC-07 | 崩溃恢复 | Main/引擎/task-worker被终止、发布前后崩溃，子树被回收，重启无重复资产/半文件成功 |
| AC-08 | 网络变化 | 断网/恢复、过期URL、DNS/redirect/代理变化、睡眠唤醒，有限重试且原因准确 |
| AC-09 | 真实下载 | 每套公开支持制品的每个声明平台均完整交付，按三种OS/架构记录，时长/轨/hash/播放符合规则 |
| AC-10 | 播放与证据 | 已声明编码组合在安装态可播，报告时间跳转正确，不支持时可用系统播放器 |
| AC-11 | 真实AI | 三套制品实测文本/视觉，输入快照与源hash一致，外部修改不污染结果，证据合格且报告可导出 |
| AC-12 | 未知调用 | 网络超时/崩溃后started转unknown，不自动重发可能计费调用 |
| AC-13 | 凭据 | 存储损坏/不可用/删除可处理，UI读取/日志/数据库/argv无明文秘密 |
| AC-14 | 资源耗尽 | 磁盘不足、并发上限、缓存清理、内存压力，原件与数据库保持一致 |
| AC-15 | 升级/备份 | 一致性备份、schema升级与失败回退通过，升级后密钥和媒体仍可用 |
| AC-16 | 正式分发 | macOS签名/公证/staple，Windows签名/安装/卸载，断网安装成立 |
| AC-17 | UI边界 | 非法IPC、非授权媒体路径、恶意Markdown和文件格式输入不能获得通用系统能力 |

性能目标先作为验收候选：参考16GB内存+SSD机器，冷启动到可操作工作区≤5秒，首版基础包空闲总内存≤600 MiB；大文件复制/hash额外内存不随文件体积线性增长。P0报告真实基线后再冻结阈值；不以该规划宣称已有测量结果。

## 10. 检查层级与风险

代码层覆盖有意义的算法、事务、幂等、取消、协议校验和恢复测试；不为每个UI包装层添加镜像实现的测试。集成层使用真实SQLite、临时目录、媒体夹具和进程，注入关键故障。Electron E2E运行已打包应用；平台/模型层另做真实Provider与完整文件验收。

| 风险 | 缓解与判定 |
| --- | --- |
| 现有Linux Runner不能跨平台 | P0先做OS adapter与冻结；不整包复制Runner |
| 平台变动与出口限制 | 少量候选、能力状态、真实支持矩阵；有本地导入替代流程 |
| 安装包资源/原生依赖遗漏 | 全新机器、明确资源路径、固定版本manifest；不借用PATH |
| 数据与文件提交不一致 | 发布意图、同卷rename、启动协调、故障注入 |
| AI未知调用重复计费 | started先落盘、unknown、显式重试、结果复用 |
| 凭据与输入传播 | Main封装、临时材料、窄IPC、日志脱敏、输入限额 |
| 软件升级损坏用户库 | 一致性备份、版本化SQL、拒绝旧schema误开、回退演练 |
| 复制源码后的规则漂移 | 迁移来源/测试登记、按版本评审同步；不运行时依赖server |
| 包体积和浏览器成本 | 先测基础包，浏览器/模型单独资源能力，按需要安装 |

阶段完成记录分别保留“实现、自动测试、安装、真实文件、真实模型、发布”状态。任一证据缺失即明确未验收；不能将规划文档、接口接线或资源数量当作产品完成。
