# 打包分发与版本升级

## 1. 构建与制品矩阵

| 系统/架构 | 首批构建环境 | 用户制品 | 运行验收 |
| --- | --- | --- | --- |
| macOS arm64 | macOS arm64原生runner | 独立DMG；自动更新阶段另产ZIP | Apple Silicon干净普通用户环境 |
| macOS x64 | macOS x64原生runner | 独立DMG；自动更新阶段另产ZIP | Intel Mac或同等真实x64环境 |
| Windows x64 | Windows x64原生runner | 完整NSIS `.exe`安装包 | Windows 11 x64干净普通用户环境 |

macOS 14+、Windows 11 x64为建议产品测试基线。最低版本在P0与选定Electron、Python wheel和FFmpeg资源兼容性一起验证并冻结；不因Electron理论支持更低版本，就声明产品在其上可用。

首版不生成Universal、不要求Rosetta、不提供Windows ARM64/Linux包。Universal需要所有Python扩展和原生依赖匹配，不能把两个冻结EXE简单合并，见 [PyInstaller平台特性](https://www.pyinstaller.org/en/stable/feature-notes.html)。

完整安装包不能在安装或首次启动时下载基础执行依赖。Windows选择`nsis`，不选择依赖在线payload的`nsis-web`，依据 [builder NSIS](https://www.electron.build/docs/nsis/)。

## 2. 随包资源

| 资源 | 打包方式 | 验证点 |
| --- | --- | --- |
| Electron、Main、Preload、React | 静态资源，JS/CSS可进ASAR | 本地页面、CSP、图标、无需Next server |
| Python引擎 | PyInstaller onedir，含解释器与动态库 | 独立运行、证书、import、sqlite实际版本、冻结资源路径 |
| yt-dlp | 固定上游制品，外置资源 | 架构、可信插件、忽略用户配置、禁用独立自更新 |
| FFmpeg/ffprobe | 固定、匹配OS/架构的可执行资源 | 元数据、合并、抽帧、全片验证、许可构建选项 |
| yt-dlp-ejs + JS runtime | 按候选平台随包提供；P0优先验证独立Deno资源 | 完整路径、版本兼容、离线proof资源，不借用用户PATH |
| 自有平台插件 | 真实目录，严格版本白名单 | frozen路径、加载成功、来源和hash |
| Skill/shared/references/modules | 引擎外置只读资源 | loader目录布局、编码、hash、NOTICE与依赖引用完整 |
| Python依赖与证书 | 随冻结结果交付 | ssl证书、动态加载和原生wheel |
| Windows Job Object适配 | 与Electron/架构匹配的最小原生模块，放可加载的ASAR外资源 | Main句柄所有权、kill-on-close、子树产生前完成绑定、干净环境可加载 |
| notices/资源manifest | 安装包内提供 | 版本、来源、SHA-256、许可证、构建配置与用途 |

可执行文件与动态库放进builder `extraResources`，通过`process.resourcesPath`定位，不能从ASAR内部直接执行；规则见 [ASAR](https://www.electronjs.org/docs/latest/tutorial/asar-archives) 与 [builder应用内容](https://www.electron.build/docs/contents/)。资源根目录不得依赖当前工作目录或源码checkout。

Python采用onedir，避免onefile每次启动解包增加冷启动和诊断难度。冻结引擎不再把`sys.executable`当通用Python命令；任务子进程使用明确的engine子命令。Windows与macOS分别生成冻结结果，不从当前Mac直接复制引擎给Windows，依据 [PyInstaller工作模式](https://pyinstaller.org/en/stable/operating-mode.html)。

当前yt-dlp完整YouTube支持还涉及ejs和JS runtime，FFmpeg/ffprobe也不是可有可无的Python包，依据 [yt-dlp依赖说明](https://github.com/yt-dlp/yt-dlp#dependencies)。PO Token/browser等额外依赖如候选样本实际需要，增加独立适配和验收，不承诺仅打包上述资源就一定恢复平台。

完整浏览器不纳入首版基础包。后续需要浏览器阶梯时，提供按OS/架构固定的可选资源包或经过验证的普通Chrome接入；其他功能不等待浏览器安装。基础包体积以P0实测为准，不预先承诺几十MB。

## 3. 资源获取与可复现构建

1. 使用固定版本和来源manifest获取资源，校验SHA-256、架构与上游签名信息；不执行不明下载脚本。
2. pnpm/uv使用冻结锁文件安装，生成协议并检查无漂移。
3. 在目标OS/架构测试引擎与动态依赖，冻结onedir。
4. 构建Main/Preload/Renderer并组合资源；先对需签名的随包可执行文件/动态库完成最终签名。
5. 对最终随包资源计算hash并写入manifest，再签最外层app、产出安装包并完成相应公证/staple。最外层app签名后不得写入或修改包内manifest。
6. 对最终已签名、已staple的DMG/EXE计算安装包hash，保存在包外发布记录；留档依赖清单和签名状态。
7. 安装最终制品后执行关键闭环；不是从源码运行E2E。

签名可能改变制品字节，因此“可复现”优先指固定源码、依赖、资源和构建步骤可追溯，不宣称带时间戳签名包逐字节相同。区分上游获取hash、最终随包资源hash和最终安装包hash；运行时校验使用最终资源字节。manifest本身不递归包含自身或最外层app签名hash。

## 4. macOS发布

正式外部分发需要Developer ID Application签名、Hardened Runtime、嵌套Python/工具可执行文件与动态库的签名、公证及staple。只给Electron最外层app签名不够；entitlements遵循所需最小集合，不用整体关闭系统保护来解决动态库问题。

以浏览器下载/复制后的实际制品测试Gatekeeper与quarantine；断网安装测试必须使用已staple制品。签名身份与bundle id稳定，升级后验证Keychain中的应用密钥仍可访问。流程依据 [Apple分发文档](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)和 [macOS签名指南](https://www.electronforge.io/guides/code-signing/code-signing-macos)。

开发期未签名包仅用于受控内部验证，不能当正式可分发产品验收。签名账户、证书与公证凭据在发布阶段准备，不写入Git或安装包。

## 5. Windows发布

默认每用户安装，路径、数据库和库目录不需要管理员权限。测试中文用户名、空格、长路径、资源被占用和卸载后的数据保留。

安装包与自有可执行文件使用Authenticode和时间戳；第三方资源签名/封装方式按所选制品验证。签名用于确认发布者与建立信誉，不能承诺消除SmartScreen提示，见 [Microsoft SmartScreen说明](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)。

任务取消和退出必须覆盖引擎及其子树；Job Object、stdio断连与正常排空组合验证。不能仅凭开发者机器中的`taskkill`成功就宣称崩溃时无孤儿进程。

## 6. 更新、数据迁移与回退

首版提供手动安装新包。后续加入可关闭的electron-updater，使用静态HTTPS feed/GitHub Releases等制品分发服务；它只提供更新文件，不承担业务。关闭更新或feed不可用不会影响启动、下载到平台或本地工作区。

macOS自动更新阶段需要相应ZIP载荷；Windows对应NSIS。发布渠道stable/beta与业务数据schema明确绑定，机制参考 [electron-updater](https://www.electron.build/docs/features/auto-update/)。

升级流程：检测版本 → 用户触发安装 → 停止新任务并排空/中断活动任务 → SQLite一致性备份及文件manifest → 校验新包 → 新版本执行有序SQL迁移 → 恢复索引/未完成任务。

迁移失败保留原数据并显示恢复入口。数据库升级后旧应用不能自动打开新schema；回退需恢复升级前的数据库快照，核对新增制品并明确新版本期间产生的数据如何导出。媒体原件不因升级被重写或删除。

首版yt-dlp/FFmpeg/插件和引擎与应用一起升级，不允许工具自行修改已签名安装目录。后续独立引擎更新若确有需要，必须有独立签名、协议兼容和原子切换，再作为专项规划。

## 7. 分发资源的许可与来源

现有源码可迁移范围要逐文件核对；Skill modules带第三方NOTICE，不能把所有资源当作项目自己的MIT代码。

FFmpeg许可证取决于实际构建启用的组件；GPL/nonfree选项改变可分发条件，见 [FFmpeg官方许可说明](https://ffmpeg.org/legal.html)。yt-dlp源码许可证与官方PyInstaller制品包含的依赖许可不同，固定制品的license要逐项登记，见 [yt-dlp制品与许可](https://github.com/yt-dlp/yt-dlp#license)。

发布前生成第三方notices、对应源码/构建信息和资源清单；选择可分发的具体二进制，不用“项目开源”代替资源核对。媒体模型权重后续另核许可，首版不随包分发。

## 8. 可交付与验收的区别

| 证据 | 可以得出的结论 |
| --- | --- |
| TS/Python测试通过 | 对应代码和夹具范围通过 |
| CI产出DMG/EXE | 构建能产生制品 |
| 已签名/公证 | 分发身份和对应制品检查通过 |
| 干净环境安装且资源可执行 | 对应OS/架构的安装及运行链路通过 |
| 真实完整媒体文件验证 | 对应平台、样本、出口和版本的下载交付通过 |
| 真实Provider分析/导出 | 对应模型能力和报告链路通过 |

正式首版需要最后三项覆盖其支持范围，不能由“CI绿色”代替。
