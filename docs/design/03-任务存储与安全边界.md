# 任务存储与安全边界

## 1. 本地契约

桌面端不复制服务端完整 HTTP DTO 或账户模型。引擎的 Pydantic 请求、结果和事件模型生成 JSON Schema 与 TypeScript 类型；Renderer 与 Main 使用同一生成结果，不手工维护第二套业务字段。

Main 自身的原生能力，例如选择文件、保存、通知和密钥写入，使用独立、窄范围的 TypeScript 契约；凡穿过信任边界的输入均需运行时校验，静态类型不是校验。

| 能力 | 命令示例 | 返回内容与边界 |
| --- | --- | --- |
| 生命周期 | `engine.hello`、`engine.shutdown` | 协议/引擎/schema版本、可用资源，不包含秘密 |
| 文件授权 | `files.choose`、`files.authorizeDropped` | Main 验证后的短期 capability；Renderer 不传任意路径执行 |
| 链接 | `media.inspect` | 元数据、语义规格、访问决策、执行上下文摘要 |
| 下载 | `downloads.create` | 持久 task id；创建与真实执行分开 |
| 导入 | `imports.create` | 持久 task id、授权文件引用 |
| 任务 | `tasks.list/get/cancel/retry` | 持久快照、revision、阶段、失败分类 |
| 资产 | `assets.list/get/reveal/export` | id、元数据、受控媒体 URL；导出需原生目录授权 |
| 分析 | `analysis.create/get` | provider/Skill快照、任务、结果引用 |
| 凭据 | `credentials.store/remove/status` | 写入与删除；查询仅返回是否存在和验证状态，不提供 readKey |
| 事件 | `tasks.changed`、`assets.changed` | id、seq、revision；触发读取事实，事件不是另一份任务状态 |

stdio 采用带 request id 的 JSON-RPC 2.0，逐行 UTF-8 framing；协议版本与应用版本分别管理。P0 默认单消息上限 1 MiB、握手期限 5 秒，结果过大使用分页或本地报告资源。视频、抽帧 base64 和完整长报告不经 stdio 传输。

stdout 只承载协议，stderr 承载限流、脱敏后的诊断。请求具备 operation id、超时和明确取消；超时表示调用方尚未得到确认，不能据此重发非幂等命令。创建任务按 operation id + payload hash 去重；重连后查询任务或原操作结果。

协议主版本不一致、资源 manifest 不匹配时不启动媒体执行，显示可修复的版本诊断。任务事件有单调 seq 和实体 revision，旧事件不能覆盖新快照；事件缺口、Renderer重载或引擎重连后重新查询快照。

## 2. 数据事实与本地 schema

Python coordinator 是唯一业务数据库 owner。Main、Renderer、任务子进程不直接打开 SQLite；所有变更经业务命令执行。长任务在事务之外运行，创建/状态迁移/事件写入在短事务中完成。

| 表 | 主要事实 |
| --- | --- |
| `assets` | asset id、管理模式、来源定位、托管相对路径、hash、大小、probe、可用状态 |
| `tasks` | 类型、状态、阶段、revision、attempt序号与随机attempt id、operation id、语义参数、取消请求、恢复原因 |
| `task_events` | 单调 seq、task id、revision、事件摘要；设保留范围并可重建快照 |
| `documents` | 源 asset、格式、提取结果引用、提取版本、解析状态 |
| `analysis_runs` | 源 asset、Skill/version/hash、Provider配置快照、结果引用与状态 |
| `analysis_steps` | 调用前 started、完成结果、结果未知、Provider请求标识与恢复决策 |
| `artifacts` | 文件用途、相对路径、hash、大小、发布阶段、所属task/analysis |
| `settings` | 非敏感设置和密钥引用；不保存明文Key/Cookie |
| `schema_migrations` | 有序SQL版本、校验和、应用版本 |

SQLite 开启 foreign keys、busy timeout 和 WAL；业务提交按耐久性目标使用 `synchronous=FULL`，进度节流后批量写入，空闲时协调 checkpoint。数据库放在本机应用数据目录，不放 NAS 或同步盘。[SQLite WAL 官方文档](https://sqlite.org/wal.html)明确约束网络文件系统，并区分 FULL/NORMAL 的断电耐久性。

P0 核对冻结 Python 实际链接的 SQLite 版本，不能只看 Python 版本。官方已记录 WAL-reset 修复边界；选用包含修复的版本并记录在资源 manifest 中。单 writer 降低竞争风险，不能替代版本核对。

桌面应用需要保留用户已安装版本的数据升级路径，因此维护显式、版本化 SQL 迁移。不得沿用服务端只维护当前态 schema 的策略。升级前一致性备份，迁移失败恢复数据库并中止升级业务，不自动删除用户数据。

## 3. 文件目录与所有权

使用 `app.getPath('userData')` 取得数据库/配置根目录，并向用户显示实际路径；不写入安装目录。媒体根目录由系统目录选择器授权。路径示意：

```text
<userData>/
  db/framefetch.sqlite
  credentials/            # Main管理的系统加密密文
  diagnostics/            # 脱敏、有大小及保留期限制
  backups/                # 元数据一致性快照；不默认包含完整媒体
<userChosenLibrary>/
  media/<asset-id>/        # 托管原件
  documents/<asset-id>/
  reports/<analysis-id>/
  cache/previews/         # 可以重新生成的预览、封面
  .staging/<task-id>/<attempt-id>/  # 每次执行隔离的未发布制品
```

| 模式 | 行为 | 删除/恢复语义 |
| --- | --- | --- |
| 引用导入（默认） | 不复制用户已有大视频；保存授权定位、大小、hash与元数据 | 文件移动/删除时标为 missing，用户重新定位；从库移除不删源文件 |
| 托管复制 | 流式复制到库、完成验证后登记 | 库管理托管副本；删除时明确区分移除记录与删除文件 |
| 平台下载 | 制品由应用写入托管目录 | 临时文件不显示为已完成；成功后才进入媒体库 |
| 导出 | 复制/生成到用户选择位置 | 不覆盖已有文件，除非保存对话框中明确确认 |

播放/重用引用资产时重新核对可用性与文件变化；hash失配标为 changed，不能把旧分析描述为新文件结果。分析绑定 asset hash 和快照。用户移除源文件不级联删除已有报告；删除分析与删除媒体分别明确选择。

文档提取和AI预处理使用本次受控输入快照：优先经过验证的COW副本，不支持时流式复制到本次暂存目录，计算副本hash并与预期asset hash核对，之后全部步骤只读该副本。硬链接不是不可变快照；复制过程中或处理前发现源内容变化时标记changed并中止，不发布旧hash对应的新报告。快照保留到相关本地步骤/分析结束，纳入磁盘预算和取消清理。

文件名由应用生成并清理非法字符、保留名、尾部点/空格和超长标题；不可将下载标题作为任意路径。支持中文、空格和非ASCII路径。移动库目录是单独的维护操作：暂停任务、复制/核对、切换定位，失败保留原库。

## 4. SQLite 与文件发布的一致性

文件系统与 SQLite 不共享一个原子事务，需要显式发布状态：

1. 数据库创建 queued task，提交之后才可执行。
2. 在最终媒体库所在卷的 `.staging/<task-id>/<attempt-id>` 中下载/复制；准备阶段写入绑定task id、attempt id、asset id和制品hash的非秘密发布意图。
3. 完成大小/hash、ffprobe、媒体轨时长和相应完整性验证，记录待发布artifact描述；协调器核对当前attempt仍有发布权且未请求取消。
4. flush/fsync文件内容后关闭句柄；工具已关闭输出时重新打开并同步。同卷atomic rename到由asset/artifact id生成的唯一最终路径，不覆盖已有成功制品，再同步父目录元数据或执行经验证的平台等效策略。
5. SQLite短事务再次核对当前attempt、取消标志和task状态；仅仍有发布权时登记asset与artifact、将task置成功，并写同revision的事件。

恢复时协调发布意图：数据库未提交而最终文件已存在，只有当前attempt仍有发布权且未取消时才能核对hash并补登记。旧attempt、已取消或失败任务的遗留文件清理/隔离，不改写终态；暂存不完整时保留可安全续传材料或清理；已登记文件缺失则标记missing，不能伪造成功制品。失败不能留下“成功”状态指向半文件。

每次重新执行产生新的attempt id，子进程事件、结果和发布意图都绑定该id。取消接受时撤销发布权；拒绝旧执行的迟到成功或错误，不允许恢复过程把cancelled改回succeeded。

跨卷不能依赖rename原子性，应先复制到目标卷暂存，再按上述协议发布。读写同名文件、Windows占用、杀进程、磁盘不足与更新中断均需故障注入验证。

atomic rename不等于断电耐久。首版数据库与托管写库优先支持经P0验证的本机APFS（macOS）/NTFS（Windows）；外接exFAT、网络卷和同步盘不纳入托管发布的耐久性承诺，可读取的源文件仍可引用导入。平台同步实现依照 [Python fsync](https://docs.python.org/3/library/os.html#os.fsync) 和对应OS能力验证，不能把POSIX目录fsync直接移植到Windows。

数据库备份使用协调器的一致性备份接口，不能运行时只复制 `.sqlite` 文件并忽略WAL；依据 [SQLite Backup API](https://sqlite.org/backup.html)。媒体备份另行选择并生成带hash的清单；API密钥不随普通备份导出，跨机器恢复后重新配置。

## 5. 任务生命周期

```text
queued -> running -> succeeded
                  -> failed
                  -> cancelling -> cancelled
                  -> interrupted -> queued / failed / needs_attention
```

`cancelling` 只表示请求已持久化；确认整个任务子树退出且临时发布停止后，才可置 `cancelled`。步骤stage与task状态分开，UI不靠百分比推断成功。

默认上限：同时下载2个、解析2个、媒体重处理1个、分析1个；各资源池协同，不能通过多个子任务绕过上限。下载前检查可用磁盘和已知体积，执行中仍处理磁盘不足；无法确定大小时显示估算，不无限占用缓存。首版视频输入目标上限20 GiB，文档50 MiB；视觉分析首版最长60分钟、最多64帧/24 MiB图像输入，用户界面解释超限与抽样策略。这些是初始产品上限，需按P0/P3实测调整，不是已验证性能。

| 中断类型 | 重启/恢复行为 |
| --- | --- |
| 导入/哈希 | 校验源文件未改变，按幂等流程重新执行；不重复登记 |
| 解析 | 重新解析，使用持久语义规格，不复用过期直链 |
| 下载 | 重新解析；相同内容/轨道/上下文且底层支持时续传，否则重新下载并说明原因 |
| 合并/抽帧/本地导出 | 临时输出隔离，幂等重做；成功原件不改写 |
| 分析尚未调用模型 | 可从已完成本地步骤恢复 |
| 模型调用started但无完成记录 | 转为结果未知并要求用户决定；不能自动再次计费 |
| 已完成模型步骤 | 验证持久结果hash后复用，不重复请求 |

不承诺所有下载都能字节级无缝续传。格式计划由分辨率、编码、容器、音轨等语义字段表示；不把yt-dlp format id或signed URL作为唯一恢复依据。

启动协调器先取得单实例与数据库所有权，检查上次未终结task与发布意图，再允许调度。Windows使用最小原生Job Object适配，启用`KILL_ON_JOB_CLOSE`，Main持有不让子进程继承的job句柄，引擎被纳入job之后才允许生成任务子树；原生模块的ABI与架构在P0验证。规则依据 [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。

macOS使用进程组、父管道失联监督和超时升级终止，进程组不会自动随父退出：Main存活时负责回收死亡task-worker的子树，Main死亡时由引擎/任务监督器检测管道失联并终止子树；引擎死亡时Main执行回收。P0还需覆盖直接终止task-worker和相关同时故障，未覆盖的强制系统故障不宣称自动无残留。PID本身不是可重用的身份，不可仅凭历史PID杀进程。

正常退出给有限停止预算，强制退出后在下次启动协调。睡眠唤醒时网络步骤重新检查连接和截止时间，过期直链重解析；不把休眠时间归为模型一定未执行。

## 6. AI 步骤与凭据

Provider 配置包含endpoint、model id、视觉/文本/结构化输出能力、超时及限额。创建分析时冻结非敏感配置与Skill hash，配置变化不悄悄修改已有任务。

先做文本或小图能力测试，视频Skill必须通过视觉能力探测；“兼容API”不能推断模型支持图像或严格schema。发送前告知将哪些抽帧/文本发往所选Provider；以预算和限额控制请求，不宣称准确的固定费用。

模型步骤持久化顺序：记录started并提交 → 请求Provider → 验证结构化结果/时间证据 → 持久结果并提交succeeded。崩溃、超时或取消后若Provider执行结果不明，保留unknown；只有能够证明未发送或明确可安全重试的错误才进入自动重试。远端取消是尽力操作，不能保证已发生的计费撤销。

Main独占持久Key的加解密。Renderer设置表单仅有写入能力，保存后清除表单值，不进localStorage、查询缓存或读取接口。引擎按有效task/provider引用索取临时材料，经私有stdio传入内存；不使用argv、环境变量、SQLite或普通日志转交Key。

safeStorage提供本机静态存储保护：macOS依赖Keychain，Windows使用DPAPI；不承诺抵御同用户恶意进程。不可用时采用当前会话内存模式并说明无法保存。[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)的API以实际锁定版本为准。这里的应用Key存储与读取Chrome平台Cookie是两件独立的事情。

## 7. Electron、文件与网络边界

- 本地业务Renderer启用context isolation和sandbox，关闭nodeIntegration；preload仅公开业务能力，不暴露通用ipcRenderer、任意fs或Shell。
- 每条IPC验证sender、frame和参数；禁止不可信远程页面获得本地preload。导航和新窗口受控，CSP不允许任意远程脚本或HTML。
- 本地媒体走限定scheme/asset id协议，Main根据授权映射打开文件，支持范围请求。请求不能包含任意绝对路径；真实路径、符号链接、越界与打开时权限都要核对。协议/session注册依据 [Electron protocol](https://www.electronjs.org/docs/latest/api/protocol)。
- 导入文件授权必须来自系统选择器或真实拖放事件；不以Renderer声明的路径代替Main验证。文件选择权限不等于全盘读取权限。
- 下载仅接收登记平台和受限HTTP(S)源，执行所有重定向、DNS、媒体清单和资源请求的校验；拒绝私网、loopback、任意shell和用户自定义下载器参数。FFmpeg清单/文档解析同样设置资源与协议限制。
- AI设置中的localhost模型endpoint是单独的显式权限，不能扩张链接下载的网络范围；用户代理配置不能关闭目标地址验证。原容器egress-proxy机制需桌面化验证，不能用一次URL检查宣称SSRF问题已经解决。
- 封面经引擎受限抓取后作为本地资源展示；外部标题、文档和模型输出作为不可信内容渲染。Markdown禁用原始HTML与不安全链接，不执行模型输出。
- 普通日志只记录task id、阶段、错误类别和摘要；不记录Key、Cookie、完整signed URL query、Prompt、抽帧或原始模型响应。

实现应遵循 [Electron官方安全建议](https://www.electronjs.org/docs/latest/tutorial/security)。子进程隔离提高容错和权限治理，但不等于完整OS沙箱；不在产品中宣称绝对文件隔离。

## 8. 后续平台身份

首版匿名平台不要求Chrome。登录平台后续优先沿用当前服务端的MV3扩展来源：普通Chrome扩展通过声明域和必要账号字段提供本次操作材料；桌面自有桥接由Main监督、绑定loopback、双向HMAC、固定扩展Origin、单配对连接、期限及大小限制。

不读取Chrome Profile文件，不调用yt-dlp浏览器Cookie解密，不复用服务器token，不要求完全磁盘访问。桥接和应用凭据分开管理；扩展分发方式、稳定ID、安装/升级、端口配对需作为独立产品专项验证，不能要求加载服务端源码目录。

macOS/Windows没有Linux tmpfs的同等默认保证。优先让必要材料只驻留内存；必须交给工具文件时使用受限ACL/权限的任务临时目录，结束/启动时清理，并说明不能保证崩溃后磁盘无残留。重新适配下载器材料输入后再决定是否允许该平台上线，不能把原tmpfs承诺照搬过来。

身份读取成功、解析成功和完整文件交付分别验收；所有登录平台必须有明确的内容范围与受保护负例，不把读取Cookie等同完整下载或官方导出授权。
